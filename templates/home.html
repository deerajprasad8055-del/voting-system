How SecureVote Works

From ballot creation to final mathematical tallying, every step guarantees uncompromising voter privacy and cryptographic integrity.

1

Register & Auth

Citizens register with a certified Voter ID. Passwords are fortified via scrypt hashing with brute-force lockout.

2

Select & Seal

A fresh 256-bit AES key and 96-bit nonce encrypt the vote payload via AES-256-GCM with authentication tags.

3

RSA Wrapping

The AES key is wrapped with the election's RSA-2048 public key using OAEP with SHA-256 padding.

4

Hash Chaining

The sealed ballot signs the previous ballot's SHA-256 hash, forming an immutable linear ledger.

5

Private Receipt

A 16-character receipt code allows the voter to verify ballot inclusion without ever exposing their vote.

6

Verified Tally

When elections close, administrators verify the chain and decrypt ballots using the private RSA key.

Defense-in-Depth Security Architecture

Built according to modern cryptographic best practices to eliminate election fraud, coercion, and ballot tampering.

RSA-2048 Asymmetric Wrapping

Keys are encapsulated with RSA-2048 using Optimal Asymmetric Encryption Padding (OAEP) with SHA-256, protecting against chosen-ciphertext attacks.

AES-256-GCM Authenticated Encryption

Every individual ballot generates a unique 256-bit symmetric key and 96-bit nonce. The 16-byte GCM authentication tag guarantees immediate tamper detection.

Cryptographic Hash Chain

Ballots are chained linearly: SHA256(prev_hash + ciphertext + wrapped_key + nonce). Any retroactively deleted, inserted, or modified ballot is caught instantly.

Triple-Layer Zero Re-Voting

Enforced strictly at the Database level (UNIQUE constraints), Server level (atomic transactional lock & rollback), and UI level (badge indicators and vote button revocation).

Absolute Voter Anonymity

The ballots table contains no user_id column. The separate vote_records table only logs that a citizen participated, never what they voted for.

Tamper-Proof Audit Trail

Administrative actions, login attempts, ballot submissions, and status transitions are recorded with client IP and timestamps in an immutable audit ledger.
